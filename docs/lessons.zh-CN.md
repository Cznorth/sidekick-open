# 跑个人 Agent 踩过的坑

[English](lessons.md) · 简体中文

这些是日常搭建和运行 Sidekick 时攒下的坑、经验和习惯，已经做了泛化：只有行为确实跟厂商有关时才保留产品名。每条按 **问题 → 经过 → 规矩** 写。

## 设备与安卓伴生 App

### 1. 激进的安卓定制系统会冻结后台应用
- **问题：** 在 HyperOS / MIUI 等系统上，只靠通知监听服务保活的伴生 App，熄屏不久就什么都收不到。
- **经过：** 就算开了前台服务、忽略电池优化，熄屏几十秒后进程照样被冻在 cgroup 里。`dumpsys activity` 仍报 `isFrozen=false`，真正的信号在 cgroup 的 `cgroup.freeze` 文件。冻结期间发给 App 的包被丢掉，服务端的 TCP 已经断了、App 还以为连着，闹钟广播也被压着不送。
- **规矩：** 常驻前台服务；收到字节就持短唤醒锁；亮屏、解锁、打开聊天页时如果连接约 30 秒没动静就重连；再加一个约 5 分钟的闹钟看门狗。排查时看 cgroup 冻结文件，不看 activity manager。告诉用户：只有把省电策略设成「无限制」并打开自启动，熄屏时消息才能准时到。

### 2. 手机睡着时超时也跟着停
- **问题：** 设备冻结或深睡时，读超时和 `wait()` 都不触发。
- **经过：** 靠这些计时器判断连接存活，连接死了很久还以为是好的。
- **规矩：** 判断连接死没死用睡眠期间也走的单调时钟（安卓上是 `elapsedRealtime`），和最后一次收到字节的时刻比。

### 3. 更新 App 会收回权限
- **问题：** 有的系统每次覆盖安装后都收回全部运行时权限和「自启动」。
- **经过：** 通知、截图、位置等数据源悄悄断了，看起来像服务端的 bug。
- **规矩：** 更新后某类数据突然断了，先怀疑权限。在设备快照里报每项权限的状态（比如「相册权限已关」），权限丢了就推一条设备事件，让 Agent 能直接告诉用户该重新授权哪一项，而不是瞎猜。

### 4. 显式监听 Wi-Fi
- **问题：** 默认网络回调漏掉了 Wi-Fi 变化。
- **经过：** 连上一个不能上网的 Wi-Fi 时，默认网络仍是蜂窝，App 根本看不到 Wi-Fi 事件。
- **规矩：** 注册网络回调时显式指定 Wi-Fi 传输类型，不依赖默认网络。

### 5. 更新后不一定能自己重启
- **问题：** 覆盖安装后，采集要等用户打开 App 才恢复。
- **经过：** 有的系统在 App 运行前就按自启动策略跳过了「包已替换」广播，多加一个广播接收器毫无用处。
- **规矩：** 用开机 / 包替换接收器在不打开界面的情况下恢复采集，然后核实进程和前台服务确实起来了（看系统的广播历史）。被厂商策略拦了就如实说，不能因为兜底重启碰巧生效就宣称修好了。

### 6. 永远不要靠卸载伴生 App 来「解决」安装问题
- **问题：** 安装报签名不一致或 `INSTALL_FAILED_USER_RESTRICTED`。
- **经过：** 卸载会清掉本地数据和所有授权；`adb install` 被厂商拦截。
- **规矩：** 所有构建用同一把固定密钥签名，安装前比对证书哈希，不一致就停。禁止卸载、降级或清数据绕过。`adb install` 受限时把 APK 推到手机上用系统安装器打开。用户正在用手机时不要打开 App 界面抢前台。

### 7. USB 调试测不出睡眠行为
- **问题：** 经 `adb reverse` 联调时一切正常。
- **经过：** USB 来的数据让设备保持响应；换成 Wi-Fi 或蜂窝、熄屏后就被冻了。
- **规矩：** 连接类的修复要走真实网络路径，分别测亮屏、熄屏和切网，再说做完。

## 接入与事件

### 8. World 要自己带鉴权入口
- **问题：** World 没有现成的外部入口。
- **经过：** 每个对接设备的 World 都起了一个小 HTTP 服务。
- **规矩：** 每个 World 一份小服务：Bearer 令牌用恒定时间比较，只收 JSON，限制请求体大小，没配令牌就不监听。换令牌时让「下一个」令牌并行放行，客户端都换好再收口。

### 9. 条目和快照是两回事
- **问题：** 把每次状态变化都推给模型会淹没上下文。
- **经过：** 电量、屏幕、应用使用的更新把真正要紧的消息挤掉了。
- **规矩：** 输入分成**条目**（通知、短信、通话：逐条一个事件，按客户端生成的稳定 ID 去重）和**快照**（实时状态、使用时长、日历：部分覆盖，只供工具查）。按类型定唤醒策略：立即叫醒、攒一下再叫醒、随下一批带上。随下一批的不能无限等，几分钟没人带走就自己投递。

### 10. 外部内容是信息，不是指令
- **问题：** 通知、短信、邮件、网页、日程正文都是第三方写的。
- **经过：** 其中任何一条都可能包含看起来像给 Agent 下指令的文字。
- **规矩：** 每个外部事件正文都标成第三方内容，并在提示词里说明。工具权限和参数校验在代码里做；打标记能减少混淆，但不是防注入。

### 11. 每个网络调用都要硬截止
- **问题：** 一次网页抓取挂住了。
- **经过：** 工具调用一直不返回，整个 Agent 循环被它卡死。
- **规矩：** 每个对外请求、每个工具调用都设硬截止时间，不依赖库自带的超时。

## 聊天与秘书

### 12. 用户只看得到显式发出的消息
- **问题：** 模型常把回答写成普通的 assistant 文本。
- **经过：** 那段文字哪儿也没去，用户只看到沉默。
- **规矩：** 发送工具是通往用户的唯一路径。一轮以普通文本结尾时退回去提醒一次（不反复提醒）。发送工具回报失败时，必须按原因修正重发才能结束这一轮；流式草稿消失不代表消息已送达。

### 13. 别往正式聊天里塞假数据
- **问题：** 为了验证，往真实会话里发了一张手拼的图片。
- **经过：** 那张 PNG 的数据块校验值是错的。一家 provider 回 400，回退的那家解析失败；因为每条消息都留在上下文里，秘书大约四个半小时一轮都没跑成。
- **规矩：** 用测试和本地起的 World 验证，不动正式聊天。非发图不可时，用真能解开的图。服务端校验附件、拒收坏图；模型拒收的图片要剥掉，不要无限重试。

### 14. 时间一律带本地日期、时刻和明确单位
- **问题：** 模型会误读相对时间和裸单位。
- **经过：** 提前量写 `1m`，被当成一个月而不是一分钟。
- **规矩：** 给模型的每个时间都带本地日期和时刻；时长用明确单位（`w`、`d`、`h`、`min`），拒绝含糊的单独 `m`。

### 15. 长回合要检查点，不要一堵墙
- **问题：** 硬轮数上限把正经活拦腰截断；上限太高，卡住的循环又白烧额度。
- **经过：** 要么做到一半停了，要么闷头空转。
- **规矩：** 用软检查点（向用户汇报进展和下一步，然后继续），硬上限只当异常兜底。一轮停在工具回执上被打断时，从下一步接着做，不重放已执行的操作，并如实告诉用户中间有空档。

## 把活派给 Coding 执行器

### 16. 传用户的原话
- **问题：** 便宜模型改写需求时会丢要求，也会编要求。
- **经过：** 执行器按转述做出了错的东西。
- **规矩：** 由代码而不是模型把用户原话附进任务。秘书可以挑其中几句，但代码逐句核对每句都是原话里连续的一段，不是就整单退回。可选的转述附在旁边、注明「以原话为准」，并发给用户核对。

### 17. 长的待拍板内容发总结，并有代码兜底
- **问题：** 执行器交回长计划、长提问，用户要在手机上拍板。
- **经过：** 等模型写总结，模型卡住时就永远等不到。
- **规矩：** 超过长度阈值就让秘书写一段短总结，连同代码生成的选项和全文链接一起发。固定时间内没等到总结，代码自己发开头。这个超时要比 provider 的重试链长，否则会被重试吃光。

### 18. 做完不等于验收
- **问题：** 「执行器结束了」被当成「任务完成了」。
- **经过：** 半截活从视野里消失；撞额度的暂停被当失败收口；中枢重启后，一个旧的失败轮次把卡又翻回了失败。
- **规矩：** 任务账本放在代码里。撞额度和提问是 `waiting`，交付是 `review`，只有用户（或获授权者）验收才是 `done`。报着在跑却几分钟没输出的会话要标出来。重启后按任务和轮次对账，旧轮次永远不能覆盖新的。

### 19. 自我更新是传话，不是特权
- **问题：** 用户希望说一句「加个功能」就能成。
- **经过：** 行得通的做法是秘书把要求原样转给负责 Agent 自身仓库的 Coding 执行器。
- **规矩：** 执行器改代码、跑测试、提交、从 main 部署，出问题能回退。运行中的 Agent 自己没有改配置、装工具的权限。「现在没这个功能」意思是「还没做」，不是「做不到」；真正的阻碍只有执行器全部离线。

### 20. 目标没完成就一直有效
- **问题：** 秘书反复让用户确认已经交代过的事的各个步骤。
- **经过：** 用户只好重说一遍，或者老要求被悄悄丢了。
- **规矩：** 用户交代的目标持续有效，直到完成、取消或被替代。排查、实现、修复、验证都是这个目标的步骤；只有改目标、扩大授权或必须用户亲手操作时才找用户。

## 模型、上下文与记忆

### 21. 收发室和秘书的上下文分开
- **问题：** 原始设备数据混进了秘书的会话。
- **经过：** 高频事件不停改写热上下文、打断请求前缀缓存，贵模型在为噪声买单。
- **规矩：** 原始数据交给用便宜模型、有独立会话的收发室，只转要紧的。工具表顺序保持稳定（World 工具在前，自有工具在后），改顺序会让缓存的前缀失效。

### 22. 用回退链，不靠干等重试
- **问题：** 各家 provider 撞额度、出故障是常态。
- **经过：** 照 `Retry-After` 等几个小时，Agent 就冻住了；坏掉的那家每条请求都要先撞一遍。
- **规矩：** 每个端点配一条有序回退列表。遇到「额度不足」和很长的 `Retry-After` 立即换下一家；冷却期落盘，重启后不再去撞已知坏掉的那家；失败的那家降级几分钟。已经开始流式输出、上下文超长（交给压缩）、用户取消时不回退。一家的加密推理不要传给另一家。

### 23. 一次性刷新令牌不能共用
- **问题：** 同一个订阅登录被复制到第二个端点和第二台机器。
- **经过：** 两边各自续期，每次续期都把对方的令牌作废。
- **规矩：** 每台机器单独登录一次；同机的其他端点借用已有登录，不复制凭据文件。

### 24. 工具名漂移要映射回来
- **问题：** 有的模型用自己训练里的工具名（`WebFetch`）去调，而不是声明的名字（`web_fetch`）。
- **经过：** 运行时回「未知工具」，Agent 读不到网页。
- **规矩：** 把返回的工具名对照本轮声明过的工具做归一（先忽略大小写，再查别名表）；目标工具本轮没声明就不改。

### 25. 快答走只读热分支
- **问题：** 一个简单的进度问题排在一个 40 分钟的回合后面。
- **经过：** 用户以为 Agent 挂了。
- **规矩：** 纯提问交给一个有界分支：复制主前缀，只能跑只读工具，截止时间很短，需要写入就把消息还给主循环。见 `core/fast-reply.mjs`。

### 26. 记忆要有上限，夜里要整理
- **问题：** 常驻记忆越长越大，挤占对话。
- **经过：** 旧内容把当前上下文挤出去；夜间重写还可能覆盖同一时刻的任务更新。
- **规矩：** 常驻记忆文件设硬上限，超了自动把最旧的行移进可检索的存档。夜里先完整存档旧记忆，再整理，最后按记忆版本和任务版本一起做比较交换。上下文到软水位时写交接笔记、换新会话。

## 工程与运维

### 27. Windows 上的 Node 与非 ASCII 路径
- **问题：** Windows 上用 Node 24 删文件。
- **经过：** 对带中文的路径 `fs.rmSync(path, { force: true })` 什么都没删、也不报错；另一次直接让进程退出。
- **规矩：** 可能带非 ASCII 文件名的文件用 `fs.unlinkSync` 删，删完核实。

### 28. 只从 main 部署
- **问题：** 一个功能分支被直接同步到了服务器。
- **经过：** 下一次从 main 部署，这个功能就被悄悄冲掉了。
- **规矩：** 先合并，再从 main 部署。worktree 可以用来开发，永远不能当部署来源。

### 29. 发版检查要机械化
- **问题：** 新的 App 包缺了上一版已有的提交。
- **经过：** 包是从旁支出的。
- **规矩：** 只从 main 发版，并在对应提交上打标签。构建前检查上一版的每个提交都在新版里、新版没有落后，不满足就报错不构建。发版说明是版本之间的 diff，不只是最新一处改动。

### 30. 生成的配置会被覆盖
- **问题：** 手改成员 Bot 的配置，改动消失了。
- **经过：** 中枢每次启动都重新生成那几段。
- **规矩：** 改生成器，不改它的输出；在文档里写明哪些段归代码管。

### 31. 自述手册和改动同一个提交更新
- **问题：** 用户会问 Agent 关于它自己的事：权限、耗电、数据从哪来。
- **经过：** 没有依据时，Agent 只能猜。
- **规矩：** 维护一份 Agent 能检索的事实性自述手册，每个主题一节、能单独看懂；改了设置、权限、采集方式或能力边界，同一个提交里更新它。

### 32. 通知只发一次
- **问题：** 部署和额度通知重复。
- **经过：** 同一件事用户收到好几条，后来干脆不看了。
- **规矩：** 按事件和档位去重（每次部署一条、每个额度窗口每档一条），用户说过不要的消息就不再发。

### 33. 个人数据永远不进仓库
- **问题：** 真实的消息和健康数据拿来当测试夹具很方便。
- **经过：** 没有泄露过，因为这条从第一天就守着。
- **规矩：** 部署目录、密钥、记忆，以及真实的健康、短信、邮件内容都不进 Git、不当夹具。夹具从头合成。每次推送前审 diff 和历史。

## 近期实战补充

### 34. 按角色分模型：长上下文的秘书，写代码交给 Coding Agent
- **问题：** 一个模型包办一切，要么处理原始数据太贵，要么做判断太弱；让聊天模型在对话里直接写代码，又慢又难审。
- **经过：** 秘书换过好几家 provider。作者现在让它跑在 1M 上下文的 Gemini 上；按他的体感，和 Claude Opus 5.5 比，遇到提示词没写到的情况时泛化明显更好，也会主动把事办完而不是再问一遍。这是日常使用感受，不是评测结论。改代码从来不由秘书自己做，而是转给在仓库里工作、会测试和提交的 Coding 执行器（Claude Code、Codex 等）。
- **规矩：** 秘书 = 你信得过做判断的最强通用模型，后面挂回退链；收发室 = 独立会话的便宜模型；代码 = Coding Agent 当执行器。所有选择写在配置里，模型变了随时换；1M 窗口是上限，不是省掉交接笔记和召回的理由。

### 35. 写记忆不能击穿前缀缓存；整理放到夜里
- **问题：** 常驻记忆文件渲染在 system 前缀里，每改写一次前缀，下一次请求就在上下文里最大、最贵的那段上缓存未命中。
- **经过：** Sidekick 里记忆工具每条事实追加一行，前缀在会话边界重新渲染；用户在 App 里手动保存记忆时，App 会提示保存会重载运行中会话的前缀、下一轮缓存失效一次。清理留给夜间的「Dream」：先把旧记忆整份存进可检索的存档（按内容哈希去重），再让秘书整理，最后和当前任务卡对账。错过的会在重启后补跑；只有秘书做梦。
- **规矩：** 白天追加，夜里重写。会话中途不改长期前缀；非改不可就改一次，接受一轮冷启动。重写前先存档；保留身份、长期事实、偏好、规则和未了事项；按记忆版本和任务版本做比较交换。

### 36. 重编译别放在小内存的主服务器上
- **问题：** 在同时跑着 Agent 的小内存服务器上编安卓包。
- **经过：** 服务器上编一次要几十分钟，还把内存挤爆；同样的构建在用户电脑上一两分钟。解决办法是一个小构建队列：电脑（它能连服务器，服务器连不进它）长轮询领活，在全新目录里编已经推上去的提交，把产物连同哈希传回；服务器核对哈希，再用正式密钥重签名。电脑只用一次性密钥签名，所以它编的包不能直接装。电脑离线或心跳断了，服务器才退回本地编，并限制内存、加锁一次只编一个。真正的编译错误原样返回，不换机器重试。
- **规矩：** 主服务器跑 Agent，不跑工具链。重编译交给更强的机器，签名密钥留在服务器，核对哈希，装前重签，本地兜底必须限资源。

### 37. 浏览器自动化用独立的用户目录
- **问题：** 拿用户日常用的浏览器做自动化。
- **经过：** 这是作者的做法，不是 Agent 仓库里记录的某次事故：自动化和日常浏览共用一个用户目录，自动化会把网站登出、改写或清掉 Cookie，用户自己的登录态就坏了。
- **规矩：** 自动化的 Chrome/Chromium 用专门的 user-data 目录启动，经 CDP 驱动；在那里有意识地登录一次。永远不要让自动化指向用户的日常配置，这个目录也不进 Git。

### 38. 手机操作放到屏幕外，日常链路去 SSH 化
- **问题：** Agent 在手机上的操作和用户抢屏幕；日常任务依赖到手机的 shell 连接。
- **经过：** 驱动手机界面的脚本会抢前台、把用户留在别的页面，所以项目定了「用户正在用手机时不许打开 App 界面」。日常采集挪到了手机本机：手机经自己带鉴权的 HTTPS 通道上传，服务端任务不再调用手机的 SSH 桥或 adb，旧的基于 shell 的采集脚本只留作人工补传。必须打开 App 的操作，作者的做法是放到虚拟屏（virtual display）里跑，这样二次跳转（一个 App 拉起另一个）不会点亮主屏、也不会抢前台。
- **规矩：** 日常业务在设备本机跑，推到带鉴权的入口；shell（SSH、adb）只用于维护。界面自动化在虚拟屏里执行，不碰用户手里那块屏幕。
